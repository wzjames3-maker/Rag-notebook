## 2. 选型理由

### 2.1 前端：Next.js (App Router)

**选择理由：**
- App Router 的 Server Components 天然适合数据密集型应用（笔记列表、知识库列表可在服务端直接查询数据库）
- Route Handlers 统一前后端代码，无需维护独立后端服务
- 与 Vercel AI SDK 深度集成，流式输出和 AI 功能开发效率最高
- 文件系统路由简化页面管理
- 内建图片优化、字体优化、代码分割

**对比 Vue 3（原方案）：**
- 原方案需 Vue 3 + Vite + Pinia + Vue Router 多个库组合，Next.js 一个框架覆盖
- React 生态的 AI/LLM 工具链（Vercel AI SDK、LangChain.js）远比 Vue 生态成熟

### 2.2 UI：shadcn/ui + Tailwind CSS

**选择理由：**
- shadcn/ui 组件以代码形式引入项目，完全可定制（非黑盒）
- 基于 @base-ui/react，无障碍支持好
- Tailwind CSS 原子化写法，响应式开发效率高
- 同时适配桌面端和移动端

**对比 Vant 4（原方案）：**
- Vant 4 是移动端优先，桌面端体验一般
- shadcn/ui 的组件质量更高，定制性更强
- Tailwind CSS 比 Vant 的 CSS-in-JS 方案更主流

### 2.3 后端：Next.js Route Handlers（单服务架构）

**选择理由：**
- 消除 FastAPI + Django 双服务架构的复杂度
- 前后端共享 TypeScript 类型，减少联调成本
- 单仓库、单部署、单进程，开发和运维成本最低
- 个人知识管理工具的并发量不需要微服务

**对比原方案（FastAPI + Django）：**
- 原方案需维护两个后端服务 + 两套代码 + 两次部署
- Django 用户服务的能力（认证/Token/文件管理）在 Next.js 中用 NextAuth + Route Handlers 完全可覆盖
- 消除服务间网络通信开销和 `DJANGO_API_URL` 配置依赖

### 2.4 数据库：PostgreSQL + pgvector

**选择理由：**
- pgvector 扩展让 PostgreSQL 同时承担关系型存储和向量检索两个角色
- 替代了原方案中 MySQL + ChromaDB + Redis 三件套，架构大幅简化
- PostgreSQL 的全文搜索（tsvector）也为后续关键词搜索提供基础
- 向量索引（IVFFlat / HNSW）性能满足万级文档规模

**对比 MySQL + ChromaDB（原方案）：**
- 原方案需要独立维护 ChromaDB 嵌入式向量库，数据与关系数据库割裂
- PostgreSQL + pgvector 在一个数据库内完成所有查询，JOIN 和事务管理更方便

### 2.5 ORM：Prisma

**选择理由：**
- TypeScript 原生支持，自动生成类型安全的查询 API
- Schema-first 设计，`schema.prisma` 即数据库文档
- Migration 工具成熟，支持增量迁移
- 与 Next.js 深度集成（推荐搭配）

### 2.6 认证：NextAuth.js v5

**选择理由：**
- Next.js 生态最成熟的认证方案
- Credentials Provider 满足用户名/密码登录需求
- JWT 策略内置支持，无需手动实现 Token 签发/刷新/黑名单
- 中间件集成（`middleware.ts`），路由保护一行代码

### 2.7 AI/RAG：Vercel AI SDK + DashScope

**选择理由：**
- Vercel AI SDK 的 `streamText` 原生支持流式输出，与 Next.js Route Handlers 零配置集成
- `useChat` hook 封装了前端流式消息渲染的全部复杂度
- DashScope 提供 OpenAI 兼容 API，通过 `@ai-sdk/openai` 自定义 baseUrl 即可对接
- `text-embedding-v3` 模型（1536 维）质量高，与 OpenAI embedding 规格一致
- 工具调用（tool calling）支持，为后续 Agent 功能预留

### 2.8 BM25 检索：orama

**选择理由：**
- 纯 JavaScript 实现，无需 Python 依赖
- 支持 BM25 评分、模糊搜索、分面搜索
- 内存索引，适合知识库规模的 BM25 检索
- 与 pgvector 向量检索配合，实现混合检索（RRF 融合）

## 3. 与原技术栈对比

| 维度 | 原方案 | 新方案 | 改进点 |
|------|--------|--------|--------|
| 前端框架 | Vue 3 + Vant 4 + Pinia | Next.js + shadcn/ui + Tailwind | 单框架覆盖、AI 生态更成熟 |
| 后端架构 | FastAPI + Django（双服务） | Next.js Route Handlers（单服务） | 消除微服务复杂度 |
| 数据库 | MySQL + ChromaDB + Redis | PostgreSQL + pgvector | 单库完成关系+向量+搜索 |
| ORM | SQLAlchemy（Python） | Prisma（TypeScript） | 类型安全、Schema 即文档 |
| 认证 | Django JWT + Redis 黑名单 | NextAuth.js v5 | 零配置 JWT、中间件保护 |
| AI 框架 | LangChain (Python) + LangGraph | Vercel AI SDK | 与 Next.js 原生集成 |
| LLM 服务 | DashScope / Ollama | DashScope（OpenAI 兼容） | 统一接口，后续可切模型 |
| 向量检索 | ChromaDB | pgvector | 无需独立向量数据库 |
| BM25 | rank-bm25 (Python) | orama (JS) | 纯 JS，无 Python 依赖 |
| 重排序 | CrossEncoder (sentence-transformers) | LLM reranking (DashScope) | 无需下载数 GB 模型权重 |
| 文档解析 | unstructured[all-docs] (Python) | pdf-parse + mammoth (JS) | 轻量，覆盖核心格式 |
| 编辑器 | bytemd | Milkdown | 插件化、更好的编辑体验 |
| 部署 | Docker Compose（3+ 容器） | Docker（仅 PostgreSQL） | 部署复杂度大幅降低 |

## 5. 已知约束

1. **DashScope API 依赖**：LLM 生成和向量化依赖阿里云百炼 API，不可完全离线运行
2. **DashScope QPS 限制**：阿里云百炼有 QPS 限制和账户余额要求
3. **pgvector 规模上限**：单用户知识库规模建议万级文档以内，超过后 IVFFlat 索引性能下降（可切换 HNSW）
4. **单文件大小**：上传文件限制 50 MB，单用户最多 500 篇文档
5. **orama 内存索引**：BM25 索引在内存中构建，知识库规模过大时需关注内存占用
