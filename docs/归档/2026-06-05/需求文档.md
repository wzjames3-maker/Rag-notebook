# RAG NoteBook — 需求分析文档

## 1. 项目背景与定位

### 1.1 背景

个人知识管理领域存在一个普遍痛点：**笔记写了从不回看，知识散落成孤岛**。主流笔记工具以记录为主，对 AI 主动召回支持薄弱，缺少"对抗遗忘"的机制。同时，LLM 技术（RAG、Agent）的成熟为"让笔记主动服务用户"提供了技术可能。

### 1.2 定位

**AI 驱动的个人知识管理工具**，以 RAG 为核心引擎，融合笔记管理、知识库检索、AI 写作辅助三个场景，解决"记而不用"的问题。

### 1.3 目标用户

- 需要 AI 辅助管理笔记和知识库的个人知识工作者
- 学生与研究人员（需要整理文献、笔记，并基于知识库进行问答）
- 技术开发者（需要检索技术文档、代码笔记）

## 3. 非功能性需求

### 3.1 性能

> 以下指标为参考值。LLM 生成速度依赖 DashScope API 和网络环境。

| 需求 | 指标 |
|------|------|
| 文档上传响应 | 小文件（< 5MB）≤ 3s（不含向量化） |
| RAG 检索响应 | 检索 + Prompt 构建 ≤ 3s（后端处理，不含 LLM 生成） |
| 流式输出 | 首 token ≤ 3s（依赖 DashScope），后续 token 流畅 |
| 笔记列表分页 | 分页查询 ≤ 500ms |

### 3.2 安全

| 需求 | 说明 |
|------|------|
| JWT 认证 | NextAuth.js v5 JWT 策略，所有 API 需有效 session |
| 用户隔离 | 数据按 userId 严格隔离（PostgreSQL 行级过滤） |
| 密钥管理 | 敏感配置通过 `.env.local` 注入，禁止硬编码 |
| SQL 注入防护 | Prisma ORM 参数化查询，无字符串拼接 |
| 密码安全 | bcrypt 哈希存储 |
| 上传文件白名单 | 限制文件类型（TXT/PDF/MD/DOCX）和单文件大小（≤ 50MB） |
| 用户容量限制 | 单用户最多 500 篇文档，知识库总容量 ≤ 2GB |

### 3.3 可用性

| 需求 | 说明 |
|------|------|
| 响应式布局 | 桌面端（≥ 1280px）+ 平板（≥ 768px）+ 手机（≥ 375px） |
| 深色/浅色主题 | next-themes + CSS 变量切换 |
| 空状态引导 | 每个列表页（笔记/知识库/会话/回收站）展示空状态 |
| 错误反馈 | API 失败统一 toast 提示，包含重试按钮 |
| Loading 骨架屏 | 列表/详情/对话页使用 skeleton 占位 |
| 确认对话框 | 所有删除操作一律二次确认 |

### 3.4 可维护性

| 需求 | 说明 |
|------|------|
| 代码规范 | ESLint + Prettier（Next.js 默认配置） |
| 类型安全 | TypeScript strict mode |
| 文档体系 | REQUIREMENTS.md + TECH_STACK.md + IMPLEMENTATION_PLAN.md + API_DESIGN.md |
| 模块化 | 按功能模块分包（lib/ai、lib/rag、components/notes 等） |

### 5.2 关键数据流

**笔记写入流：**
```
用户编辑 → NoteEditor → PUT /api/notes/[id]
  → Prisma 写入 PostgreSQL
  → 返回成功响应
```

**RAG 问答流：**
```
用户提问 → ChatInput → POST /api/chat
  → DashScope 向量化问题
  → 并行检索：
    → pgvector cosine similarity → top 20
    → orama BM25 → top 20
  → RRF 融合 → top 10
  → LLM Rerank (DashScope) → top 5
  → 构建 Prompt（system + context + history + question）
  → Vercel AI SDK streamText → 流式生成
  → 持久化 ChatMessage
→ 流式返回前端（含 sources 引用）
```

**文档上传流：**
```
用户上传文件 → FileUpload → POST /api/knowledge/upload
  → 计算 MD5 → (userId, md5) 去重检查
  → 解析文档（pdf-parse / mammoth / 原生读取）
  → 文本切片（~500 tokens, overlap 50）
  → DashScope 批量向量化
  → 写入 KnowledgeChunk + pgvector
  → 更新 KnowledgeDocument 状态
→ 返回上传结果
```

**用户登录流：**
```
用户提交表单 → Login → NextAuth signIn("credentials")
  → bcrypt 校验密码
  → 签发 JWT session
  → middleware.ts 保护路由
→ 跳转 Dashboard
```

## 6. 约束与假设

### 6.1 技术约束

- **DashScope API 依赖**：LLM 生成和向量化依赖阿里云百炼 API，不可完全离线运行
- **DashScope QPS 限制**：阿里云百炼有 QPS 限制和账户余额要求，欠费或超限会导致 LLM 调用失败
- **pgvector 规模上限**：单用户知识库规模建议万级文档以内，超过后 IVFFlat 索引性能下降（可切换 HNSW）
- **orama 内存索引**：BM25 索引在内存中构建，知识库规模过大时需关注内存占用
- **单文件上传限制**：50 MB，单用户最多 500 篇文档

### 6.2 运行环境假设

- Node.js 18.18+ 运行环境
- Docker 可用（本地 PostgreSQL 容器）
- pnpm 包管理器
- 网络环境可访问 DashScope API（国内）
- 磁盘空间 10 GB+（node_modules + 数据库）
